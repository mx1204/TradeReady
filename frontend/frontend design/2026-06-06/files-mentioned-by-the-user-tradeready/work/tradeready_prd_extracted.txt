Purpose 
The purpose of this document is to define the requirements, scope, and execution plan for 
TradeReady — an AI system that converts a plain-language product description and a 
destination country into a complete, jurisdiction-specific trade compliance package in under 60 
seconds. 
 
TradeReady is being built for the Sea x OpenAI Codex Hackathon (Build Direction 2: AI-Native 
Products & Operations and Build Direction 3: Deep Domain AI). It demonstrates what 
compliance infrastructure looks like when AI shapes the process fundamentally, rather than 
augmenting a manual workflow. 
 
Project Scope at a Glance 
TradeReady will deliver a functional, web-based proof-of-concept that: 
• Accepts a plain-language product description and a destination country (Singapore, 
Malaysia, Indonesia, Thailand, Vietnam) as inputs. 
• Identifies the correct HS-6 code for the product using a frontier reasoning model. 
• Computes applicable import duties and taxes for the destination jurisdiction. 
• Performs a restricted goods check, including certification requirements (e.g. BPOM for 
Indonesia, SIRIM for Malaysia). 
• Generates a completed, ready-to-submit commercial invoice and customs declaration 
document specific to the destination country. 
• Surfaces a jurisdiction diff when a seller switches destination country, showing exactly 
what changes across duties, restrictions, and documentation. 
• Delivers all outputs in under 60 seconds via a Codex-powered agentic workflow with a 
critic agent for accuracy validation.

Overall Description 
Project Background 
Cross-border e-commerce in Southeast Asia is growing rapidly, but compliance infrastructure 
has not kept pace. The five primary markets — Singapore, Malaysia, Indonesia, Thailand, and 
Vietnam — each maintain distinct customs regimes, duty schedules, restricted goods 
frameworks, and documentation requirements. Although the Harmonised System (HS) 
classification framework provides a common global foundation, sellers routinely encounter 
critical compliance gaps at the HS-6 level, where country-specific interpretations diverge. 
 
A Shopee seller expanding from Singapore to Indonesia today faces a decision: engage a 
customs broker at significant cost, or self-classify and risk errors. The consequences of errors 
are material: U.S. courts have issued multi-million dollar penalties over customs duty evasion 
tied to incorrect trade declarations, and Singapore Customs has pursued freight forwarders for 
false declarations. Enforcement is escalating and compliance errors are increasingly treated as 
serious breaches, not harmless paperwork glitches. 
 
The problem is compounded by product-level regulatory variation. Cosmetics entering Indonesia 
require BPOM certification. Electronics entering Malaysia require SIRIM approval. Food 
products, medical devices, and chemicals carry their own certification stacks. SME sellers are 
expected to manage enterprise-grade compliance without dedicated trade teams, legal counsel, 
or customs brokerage relationships. 
 
TradeReady is built on the observation that trade compliance — despite its perceived 
complexity — is a structured, rule-based workflow that can be made AI-executable. Regulatory 
rules are deterministic given a product and jurisdiction. The value of AI here is not in generating 
approximations, but in retrieving current regulatory data, mapping it precisely to a product, 
executing the compliance workflow, and producing auditable structured outputs that can be 
submitted directly to customs authorities. 
 
Product Perspective 
TradeReady is architected as a standalone web application with an agentic backend. It does not 
integrate with existing ERP, marketplace, or customs brokerage systems in this proof-of-
concept phase, though the architecture is designed to support such integrations as future work. 
 
The system operates as an end-to-end compliance workflow engine. A seller interacts with a 
clean, minimal frontend. The backend orchestrates a multi-agent pipeline: a classification agent 
for HS-6 mapping, a duty computation agent, a restricted goods agent, a document generation 
agent powered by Codex, and a critic agent that cross-checks all outputs against retrieved 
regulatory source data before returning a result.

Product Functions 
At the highest level, TradeReady performs five classes of function: 
• HS-6 Classification. Given a plain-language product description, the system maps the 
product to the correct six-digit Harmonised System code, applying country-specific tariff 
schedule interpretations for the destination jurisdiction. 
• Duty and Tax Computation. The system retrieves and applies the current import duty 
rate, VAT/GST rate, and any applicable excise or additional taxes for the destination 
country, computing a total landed cost estimate. 
• Restricted Goods and Certification Check. The system identifies whether the product 
falls within a restricted, prohibited, or certification-required category for the destination 
jurisdiction, and surfaces the applicable regulatory requirements. 
• Document Generation. Codex generates a completed, ready-to-submit customs 
declaration and commercial invoice in the format required by the destination country's 
customs authority. 
• Jurisdiction Diff. When a seller changes the destination country, the system regenerates 
the compliance package and surfaces a structured diff showing what changes across 
duties, restricted categories, certification requirements, and documentation.

Operating Environment 
TradeReady will be deployed as a web application accessible from any modern desktop or 
mobile browser. The frontend is implemented as a single-page application (React). The 
backend runs on a single server and exposes a REST API consumed by the frontend and 
available for direct integration. The agentic pipeline runs server-side; no sensitive regulatory 
retrieval logic is exposed to the client.

Design and Implementation Constraints 
• Single-server deployment. The hackathon proof-of-concept runs on one server. 
Distributed deployment and high-availability architecture are identified as future work. 
• Supported jurisdictions. The initial release supports five destination countries: 
Singapore, Malaysia, Indonesia, Thailand, and Vietnam. HS code classification uses the 
HS-6 level, which is internationally harmonised; duty rates and restricted goods rules are 
jurisdiction-specific. 
• Regulatory data freshness. Duty rates and restricted goods rules are retrieved from 
official customs portals via a RAG pipeline with scheduled refresh cadences. The system 
does not guarantee real-time accuracy; outputs include a data-freshness timestamp and 
source citation. 
• Document output scope. Generated documents cover commercial invoices and primary 
customs declarations for each supported jurisdiction. Certificate applications (e.g. 
BPOM, SIRIM) are flagged and described but not generated in the proof-of-concept 
phase. 
• Build timeframe. The full build takes place on a single day (6 June 2026). Stretch goals 
are tracked separately and pursued only after base requirements are met. 
 
Assumptions and Dependencies 
• Official customs portals for supported jurisdictions (customs.gov.sg, beacukai.go.id, 
customs.gov.my, customs.go.th, customs.gov.vn) are publicly accessible and machine-
readable. 
• OpenAI API access (including Codex) is provided to all participants during the hackathon 
event. 
• Sellers can provide a plain-language product description sufficient for HS-6 
classification. The system will prompt for clarification if the description is ambiguous.

Problem Statement 
SME sellers operating cross-border in Southeast Asia face a compliance bottleneck that scales 
with the number of destination markets they enter. The Harmonised System provides a globally 
standardised classification framework, but correct HS-6 mapping requires jurisdiction-specific 
expertise. Duty rates, VAT/GST thresholds, restricted goods rules, and documentation 
requirements vary materially across Singapore, Malaysia, Indonesia, Thailand, and Vietnam. 
 
Existing tools force sellers into one of three inadequate options: engage a customs broker 
(expensive, slow), rely on generic HS lookup tables (inaccurate at the jurisdiction level), or 
guess (legally and financially risky). Enforcement is escalating. Singapore Customs has pursued 
freight forwarders for false declarations. Indonesian customs authorities have levied significant 
fines for misclassified electronics and cosmetics. Compliance errors are no longer treated as 
harmless paperwork mistakes. 
 
Product-level regulatory requirements compound the problem. Cosmetics entering Indonesia 
require BPOM certification. Electronics entering Malaysia require SIRIM approval. Sellers must 
manage an expanding matrix of country-by-product rules without the compliance infrastructure 
of large enterprises. 
 
TradeReady resolves this by turning trade compliance into an AI-executable workflow. Given a 
product description and a destination country, the system retrieves current regulatory data from 
official sources, classifies the product to HS-6, computes duties and taxes, checks restricted 
goods rules, and generates ready-to-submit documentation — in under 60 seconds, with full 
source citations and a critic-validated confidence score.

Research Summary 
Limitations of Current Compliance Approaches 
Traditional customs brokerage is the default for compliant cross-border trade, but it is 
inaccessible to SMEs at scale. Brokers charge per-shipment fees that are proportionally 
punishing for low-value e-commerce parcels, introduce multi-day turnaround times, and provide 
outputs that are opaque to the seller — a PDF invoice with no explanation of the classification 
rationale or regulatory basis. 
 
Self-service HS lookup tools (WCO databases, national tariff portals) require users to navigate 
multi-level hierarchical classification trees with technical product descriptions. Error rates among 
non-specialist users are high. A World Customs Organisation study found that a significant 
proportion of HS classifications submitted by SMEs contain errors at the 6-digit level. 
 
Market Context 
The Southeast Asian cross-border e-commerce market is projected to reach USD 102 billion by 
2025 (Google, Temasek, Bain & Company e-Conomy SEA report). Shopee and Lazada each 
operate across five or more jurisdictions. The seller base is predominantly SME: in Indonesia 
alone, over 21 million sellers operate on digital commerce platforms (Statista, 2024). The 
compliance gap is not a niche problem; it is a structural bottleneck affecting the majority of 
cross-border sellers.

Non-Functional Requirements 
Performance Requirements 
• End-to-end compliance package generation (HS-6 classification, duty computation, 
restricted goods check, document generation) must complete in under 60 seconds for a 
standard product description and single destination country. 
• Jurisdiction diff generation must complete in under 90 seconds (includes regeneration of 
full compliance package for the new jurisdiction). 
• The web application must load in under 3 seconds on a standard broadband connection. 
• The system must handle at least 10 concurrent compliance requests without degradation 
in response time during the hackathon demonstration. 
 
Accuracy Requirements 
• HS-6 classifications must be accompanied by a confidence score derived from the critic 
agent's cross-check against retrieved source data. 
• Outputs where the critic agent detects a mismatch above the confidence threshold must 
be automatically re-processed against a secondary regulatory source before being 
returned to the seller. 
• All duty rates and regulatory rules surfaced by the system must be traceable to a specific 
URL and publication date from an official customs portal. 
• The system must not return a compliance package without a complete source citation 
chain. 
 
Security Requirements 
• All client-server communication must occur over TLS 1.3 or later. 
• Product descriptions and compliance outputs submitted by sellers must not be retained 
beyond the session without explicit consent. 
• API keys and regulatory data credentials must not be exposed in client-side code or 
logs. 
 
Usability Requirements 
• A seller unfamiliar with HS codes must be able to complete a compliance request in 
under three interactions: enter product description, select destination country, receive 
output. 
• All outputs must be expressed in plain language. HS codes must be accompanied by 
plain-language descriptions. Technical regulatory terms must be explained in context. 
• The jurisdiction diff must be immediately readable by a non-specialist — changed fields 
must be visually distinct and changes must be described in plain language, not 
regulatory jargon. 
• The system must be responsive and usable on mobile, tablet, and desktop viewports. 
---PAGE---
 
Reliability and Availability Requirements 
• The system must maintain availability throughout the hackathon demonstration period. 
• If a regulatory data source is unavailable at query time, the system must serve from the 
most recently cached version and indicate the cache date to the seller. 
• Compliance packages must not be partially returned; the system must either return a 
complete package or a clear error with a retry option. 
 
Auditability Requirements 
• Every compliance package must include a full provenance record: input product 
description, HS-6 code with rationale, regulatory sources retrieved, duty rates applied, 
restricted goods determination, and document generation parameters. 
• All compliance outputs must be downloadable as structured JSON in addition to human-
readable PDF, enabling downstream integration and audit.

System Features 
Intelligent HS-6 Classification 
A seller enters a plain-language product description. The classification agent retrieves relevant 
sections of the destination country's tariff schedule via the RAG pipeline and uses a frontier 
reasoning model to map the product to the correct six-digit HS code. The output includes the 
HS-6 code, the official HS description, a plain-language rationale, and a confidence score. This 
is the foundation of the entire compliance workflow — all subsequent steps are computed from 
the HS-6 classification. 
 
Real-Time Duty and Tax Computation 
Given the HS-6 code and destination jurisdiction, the duty agent retrieves the current import 
duty rate from the official tariff schedule, computes applicable VAT/GST, and identifies any 
excise or additional taxes. The output is an itemised computation showing each rate applied, the 
regulatory basis, and an estimated landed cost. All rates are sourced directly from official 
customs portals and include a freshness timestamp. 
 
Jurisdiction-Specific Restricted Goods Check 
The restricted goods agent checks the product against the destination country's restricted goods 
list, prohibited goods list, and certification requirement database. Products are classified as 
unrestricted, conditional (certification required), restricted (import permit required), or prohibited. 
For conditional and restricted products, the system surfaces the applicable certification body, 
required documentation, and estimated processing timeline. BPOM requirements are surfaced 
for cosmetics entering Indonesia; SIRIM requirements for electronics entering Malaysia. 
 
Codex-Powered Document Generation 
The document generation agent uses Codex to convert regulatory rules into executable Python 
workflows that produce completed, filled customs documents. Outputs are jurisdiction-specific: a 
completed Pemberitahuan Impor Barang form for Indonesia; a commercial invoice aligned to 
Singapore Customs requirements for Singapore; equivalent primary declaration documents for 
Malaysia, Thailand, and Vietnam. Documents are available as PDF downloads and as 
structured JSON for downstream processing. 
 
Critic Agent Validation 
After each agent completes its step, the critic agent cross-checks the output against the 
retrieved regulatory source data. When a mismatch exceeds a confidence threshold, the critic 
triggers an automated re-query against a secondary regulatory source, reconciles the data, and 
re-runs the affected workflow step. Only if the discrepancy persists after reconciliation is the 
output flagged for human review. This validation loop is the mechanism by which TradeReady 
distinguishes itself from tools that generate plausible but unverified regulatory outputs. 
---PAGE---
 
Jurisdiction Diff 
When a seller switches destination country, TradeReady regenerates the full compliance 
workflow and surfaces a structured diff. Changed fields are highlighted across four dimensions: 
import duty rate and amount, VAT/GST rate and threshold, restricted goods status and 
certification requirements, and documentation format. The diff makes regulatory differences 
immediately actionable rather than requiring the seller to research them independently.

Codex Integration 
TradeReady uses Codex as its document generation engine. Rather than producing static 
template-filled outputs, the document generation agent uses Codex to convert regulatory rules 
into dynamically generated Python workflows that are executed per shipment. This approach 
produces structured, auditable outputs — each document is generated by a traceable piece of 
code that reflects the regulatory logic applied — rather than text completions that may silently 
omit required fields. 
 
Codex is also used to adapt document generation logic when regulatory requirements change, 
enabling the system to update its output format by regenerating the relevant workflow rather 
than requiring manual template maintenance. 
---PAGE---
 
RAG Pipeline Design 
Regulatory data is retrieved from official customs portals for each of the five supported 
jurisdictions. The scraping schedule is calibrated to each portal's update frequency: Singapore 
Customs and Royal Malaysian Customs publish tariff updates quarterly; Bea Cukai (Indonesia) 
publishes updates monthly; Thai Customs and Vietnam General Department of Customs 
publish on irregular schedules and are scraped weekly. 
 
Retrieved data is structured into domain-specific chunks (HS chapter, duty rate table, restricted 
goods list, certification requirement, documentation requirement), embedded using a text 
embedding model, and stored in a vector store indexed by jurisdiction and HS chapter. At query 
time, the retrieval step surfaces the most relevant chunks for the given HS-6 code and 
jurisdiction, along with source URL and publication date.

retrieval can be tuned against these cases.

Regulation and Compliance 
Data and Privacy 
TradeReady processes product descriptions submitted by sellers. In the proof-of-concept 
deployment, no personally identifiable information is required. Product descriptions and 
compliance outputs are not retained beyond the session. The system is designed from the 
outset to be compatible with the Singapore Personal Data Protection Act (PDPA) obligations 
applicable to the development environment. 
 
Regulatory Data Usage 
TradeReady retrieves regulatory data from publicly accessible official government customs 
portals for informational and compliance-assistance purposes. All outputs include source 
citations directing sellers to the original official source. TradeReady does not represent itself as 
a customs authority and all outputs carry a plain-language disclaimer that they are AI-generated 
and should be verified before submission to customs authorities. 
 
Disclaimer of Fitness for Purpose 
All deliverables and released artefacts carry an explicit disclaimer that TradeReady is a proof-of-
concept demonstration. Outputs have not been independently audited and are not certified for 
use as the sole basis for customs declarations in any jurisdiction. Sellers are advised to verify all 
outputs against official sources and to seek professional customs advice for high-value or 
complex shipments. 
 
Open-Source Licensing 
Source code produced during the hackathon will be released under the Apache 2.0 licence. All 
third-party libraries and dependencies used carry compatible permissive licences.
